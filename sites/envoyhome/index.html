What is EnvoyHome?

A household agent you own — not a cloud chatbot with a home-themed name.

EnvoyHome is the household agent in the EnvoyMesh apps family. The core is the agent loop itself: envoy-harness, static workflows, memory, approvals, and a rich tool catalogue the agent can use — files, web, browser, office documents, skills, schedules, MCP, and more.

The agent lives on the home computer. Keys, transcripts, sandboxes, and smart-home credentials stay there. Desktop and phone dial in over the home.* channel; they are windows, not brains.

Smart home is one tool surface among those capabilities — useful when you connect a hub, never the definition of the product. EnvoyHome enhances Home Assistant and MQTT with natural language, approvals, and workflows. It does not replace your hub, and it does not ship a social network.

🏠

The agent stays home

Every chat, workflow, and scheduled turn runs through the home daemon. Thin clients reconnect to it — they never hold the model keys or run the loop.

🔁

Workflows are not a second engine

Static DAGs in a visual diagram or YAML, drafted from natural language. Workflow nodes call the same tools as chat, with the same approvals.

🛡️

Approvals before consequences

Durable pending approvals, a 600-second default TTL, fail-closed decisions, and grants bound to the resolved call — not a blanket “agent may do anything” switch.

🧠

Memory that learns carefully

Profile, standing notes, daily logs, episodic search, KnowYou, a document knowledge base, and skills — with PendingLearn gating the durable writes.

👨‍👩‍👧

One agent, many people

Household profiles share the agent but keep isolated memory, files, and policy. Phones pair to the house, and each device is bound to the accounts it may act for.

🔀

Cloud, local, or careful mix

Bring an OpenAI-compatible or Anthropic-compatible provider, run llama.cpp locally, or connect Ollama. Privacy Mode forces local turns and can block smart-home egress.

🧰

A real tool catalogue

Files behind a path jail, web search and reading, a browser with form cards, office document import/export, skills, sessions, MCP servers, and optional HA/MQTT tools.

🧩

Skills pass a verify gate

The on-disk format is a SKILL.md directory. Install from disk, a URL, or ClawHub — then verify capabilities before the skill can run. Agent-authored skills wait in PendingLearn.

⏰

Schedules, heartbeat, standing orders

Repeating or one-shot jobs, natural-language “when” proposals you confirm, a heartbeat for periodic review, and standing orders that survive restarts.

Eight layers, one honest memory

EnvoyHome does not treat “everything is memory” as a design. Each layer has a job, a budget, and an injection rule — so the agent can remember without quietly rewriting who you are.

  • Working memory is the session transcript, flushed before compaction rather than silently truncated.
  • Standing memory is small and capped: profile facts, MEMORY.md, and the last two days of notes.
  • Lookup memory is a tool: episodic search, KnowYou, and your document knowledge base with citations.
  • Durable writes go through PendingLearn — you accept or reject the proposed diff before L1, L2, or a skill changes.

Smart home, with a safety class

Connect Home Assistant or an MQTT broker and the agent can read state and — with approval — call services. It integrates with your hub; it does not become one.

  • Actuation is admin, not a file write. Unattended turns need a matching grant; script, scene, and button indirection is denied by default.
  • Safety-class calls never ride a grant. Locks, alarms, garage doors, gates, valves, unlisted MQTT topics, and anything marked neverUnattended ask every single time.
  • Unknown means safety-class. A new domain, a vendor extension, or a topic you did not allow-list fails closed instead of guessing.
  • Bind before control. Objects are registered by the authenticated hub and resolved through a chokepoint — never from a plugin-asserted id.

Preview posture: Home Assistant REST tools and MQTT publish work today, with bundled demo hubs for the full Chat → Approvals path. Live inbound event plumbing and a signed-off live household still follow the operator checklist.

Security is the product, not a page

Shared-home defaults: sandbox on, approvals durable, unknown things fail closed.

Identity

No account, no cloud mailbox

Identity is an Ed25519 key pair on your devices. There is no EnvoyHome sign-up, no email address, and no hosted transcript store to breach.

Approvals

Durable and fail-closed

Pending approvals and grants are files per account. A restart keeps the question; a timeout resolves to deny; an unresolvable principal is denied.

Execution

Path jail and risk tiers

File tools resolve through one jail. Tools declare read, write, exec, network, admin, or sensitive — and can escalate, never de-escalate.

Privacy

Privacy Mode

A hard switch that forces local turns and refuses cloud tools. With smart-home egress blocking on, it also refuses actuation and event-source notifications.

Accounts

Household isolation

Memory, transcripts, files, grants, and policy are keyed by account. A paired device may only act for the accounts it is bound to.

Smart home

The physical world is different

Actuation is admin. Camera, lock, and presence data is sensitive and forces local inference. Device state never becomes standing memory automatically.

Run it at home

Preview builds run from source. You need Node.js 22+, pnpm, and a sibling EnvoyMesh checkout.

1

Check the siblings

EnvoyHome links @envoymesh/* with link: — they are not on npm. The peer check fails closed if a sibling is missing or on the wrong branch.

./scripts/peers-check.sh
# or set ENVOYHOME_PEERS_GIT_BASE and run ./scripts/fetch-peers.sh
2

Install and build

Never install with CI=true set — pnpm’s strict-mode trap is a documented convention in this repo.

env -u CI pnpm install
pnpm -r build
3

Start the home agent

Run the daemon alone, or let the desktop shell supervise it. Then create a profile, add a model, and pair a phone when you want one.

pnpm run dev:daemon   # daemon only
pnpm desktop:dev      # Tauri Settings shell

Run the desktop app from source

Node.js ≥ 22 and pnpm 10.33 (the root packageManager), a sibling EnvoyMesh checkout, and Rust plus the Tauri CLI prerequisites for the desktop shell.

./scripts/peers-check.sh
env -u CI pnpm install
pnpm -r build
pnpm desktop:dev        # daemon build if missing, then Tauri dev

desktop:dev runs ./scripts/desktop-dev.sh: it builds packages/daemon/dist/bin/envoyhome-daemon.js only when that file is missing, then starts tauri:dev. Tauri supervises the daemon once the binary exists. No provider config file is needed before launch — first-run Settings asks for a profile and a model provider (preset + key, or Local / Ollama).

Release bundle: pnpm desktop:tauri:build · installers: pnpm desktop:build macos (push credentials required unless REQUIRE_PUSH_CREDENTIALS=0).
